# Отчёт: контейнеризация веб-приложения с помощью Docker

**Проект:** сайт-витрина «Жанара — AI Creator» с админ-панелью
**Дата:** 7 октября 2026 г.
**Инструменты:** Docker 29.8.2, Docker Compose v5.5.1, Node.js 24

---

## 1. Цель работы

Упаковать готовое веб-приложение в Docker-контейнер, чтобы:

- приложение запускалось одной командой на любом компьютере с Docker, без ручной установки Node.js и зависимостей;
- окружение было одинаковым при разработке и при размещении на сервере;
- данные (база, загруженные файлы) хранились отдельно от кода и не терялись при обновлении приложения;
- старый способ запуска (через планировщик заданий Windows) был заменён на запуск через Docker без потери данных.

## 2. Описание приложения

| Часть | Технология | Назначение |
|---|---|---|
| Фронтенд | React 19, сборщик Vite 8 | Витрина сайта (`index.html`) и админ-панель (`admin.html`) |
| Бэкенд | Node.js 24, Express 4 | REST API, раздача собранного фронтенда и картинок |
| База данных | SQLite (встроенный модуль `node:sqlite`) | Товары, заказы, клиенты, сессии |
| Файлы | Папка `uploads/` | Картинки товаров |
| Дополнительно | OpenAI API, Telegram Bot API, PDFKit | Чат-бот, уведомления о заявках, генерация PDF |

Особенность, важная для Docker: SQLite встроен в Node.js 24, поэтому в образе не нужно компилировать нативные модули. Это упрощает сборку.

## 3. Созданные файлы

### 3.1. `Dockerfile` — инструкция сборки образа

Использована **многоэтапная сборка (multi-stage build)** из трёх этапов:

```dockerfile
# syntax=docker/dockerfile:1

# Этап 1: сборка фронтенда (нужны dev-зависимости, в том числе Vite)
FROM node:24-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY vite.config.mjs index.html admin.html ./
COPY src ./src
RUN npm run build

# Этап 2: установка только боевых зависимостей
FROM node:24-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

# Этап 3: итоговый образ
FROM node:24-slim
ENV NODE_ENV=production \
    HOST=0.0.0.0 \
    PORT=3000
WORKDIR /app

COPY --from=deps /app/node_modules ./node_modules
COPY package.json server.js ./
COPY server ./server
COPY scripts ./scripts
COPY img ./img
COPY --from=build /app/dist ./dist
COPY uploads ./uploads

RUN mkdir -p data/logs data/backups && chown -R node:node data uploads
USER node

EXPOSE 3000
VOLUME ["/app/data", "/app/uploads"]

HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3000/api/ready').then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"

CMD ["node", "server/index.js"]
```

**Обоснование решений:**

| Решение | Зачем |
|---|---|
| Базовый образ `node:24-slim` | Нужна версия Node.js 22.13+ для `node:sqlite`; вариант `slim` меньше полного образа |
| Многоэтапная сборка | Vite и исходники `src/` нужны только для сборки; в итоговый образ попадает лишь готовая папка `dist/` и боевые зависимости |
| Сначала `package.json`, потом код | Слой с `npm ci` кэшируется: при изменении кода зависимости не переустанавливаются, пересборка идёт быстрее |
| `npm ci` вместо `npm install` | Точная установка версий из `package-lock.json`, сборка воспроизводима |
| `USER node` | Приложение работает не от root — меньше последствий при взломе |
| `HOST=0.0.0.0` | По умолчанию сервер слушает только `127.0.0.1`; внутри контейнера это сделало бы его недоступным снаружи |
| `HEALTHCHECK` | Docker сам проверяет, что приложение живо и база доступна (эндпоинт `/api/ready`) |
| `VOLUME` | Папки с данными выносятся в тома и не хранятся в слое контейнера |

### 3.2. `.dockerignore` — что не попадает в образ

```
node_modules
dist
data
uploads/*
!uploads/product-*.jpg
public
test
.env
.env.*
.git
.gitignore
.vscode
*.bat
*.log
tmp-product.jpg
help.txt
Dockerfile
docker-compose.yml
.dockerignore
```

Это важно по двум причинам:

1. **Безопасность.** Файл `.env` с паролем админки и API-ключами не попадает в образ. Секреты передаются только при запуске контейнера. Так образ можно передавать другим людям без утечки ключей.
2. **Размер и скорость.** Не копируются `node_modules` с хоста (они ставятся внутри, под Linux), база с личными данными клиентов, тесты, логи.

### 3.3. `docker-compose.yml` — описание запуска

```yaml
services:
  app:
    build: .
    image: zhanara-site
    container_name: zhanara-site
    restart: unless-stopped
    env_file: .env
    environment:
      HOST: 0.0.0.0
      PORT: 3000
    ports:
      - "127.0.0.1:${APP_PORT:-3000}:3000"
    volumes:
      - site-data:/app/data
      - site-uploads:/app/uploads
    stop_grace_period: 15s

volumes:
  site-data:
  site-uploads:
```

| Параметр | Назначение |
|---|---|
| `restart: unless-stopped` | Контейнер перезапускается после сбоя и после перезагрузки компьютера |
| `env_file: .env` | Секреты (пароль, ключи) подставляются при запуске, а не при сборке |
| `ports: 127.0.0.1:3000:3000` | Сайт доступен только с этого компьютера; для публичного доступа нужен reverse proxy с HTTPS |
| `volumes` | Именованные тома: данные переживают пересоздание и обновление контейнера |
| `stop_grace_period: 15s` | Время на корректное завершение (сервер обрабатывает сигнал SIGTERM и закрывает базу) |

**Почему именованные тома, а не папка с диска Windows.** SQLite в режиме WAL использует разделяемую память и блокировки файлов. На папках Windows, подключённых в Linux-контейнер, это работает ненадёжно и может повредить базу. Именованный том Docker хранится внутри Linux-окружения, и таких проблем нет.

## 4. Ход работы

1. **Анализ проекта.** Изучены `package.json`, конфигурация сервера (`server/core/config.js`), сборщик (`vite.config.mjs`), раздача статики. Выяснено: какие папки нужны во время работы, где хранятся данные, какие переменные окружения читает сервер, есть ли эндпоинты проверки состояния.
2. **Написание** `Dockerfile`, `.dockerignore`, `docker-compose.yml`.
3. **Сборка образа:** `docker compose build`. Сборка прошла успешно примерно за 45 секунд, фронтенд собрался внутри контейнера.
4. **Тестовый запуск** на отдельном порту 3001, без данных и без `.env`, чтобы не мешать работающему сайту:
   ```powershell
   docker run -d --rm --name zhanara-test -p 127.0.0.1:3001:3000 zhanara-site
   ```
5. **Резервная копия** папок `data/` и `uploads/` перед переносом.
6. **Остановка старого способа запуска.** Сайт работал через задачу планировщика Windows `ZhanaraSite` и супервизор `scripts/supervisor.js`. Задача удалена, процессы остановлены, чтобы освободить порт 3000.
7. **Перенос данных в тома Docker:**
   ```powershell
   docker compose create
   docker compose cp .\data\site.db app:/app/data/site.db
   docker compose cp .\data\site.db-wal app:/app/data/site.db-wal
   docker compose cp .\data\backups\. app:/app/data/backups/
   docker compose cp .\uploads\. app:/app/uploads/
   docker compose run --rm --no-deps -u root --entrypoint chown app -R node:node /app/data /app/uploads
   ```
   Последняя команда назначает владельцем файлов пользователя `node`, от которого работает приложение.
8. **Запуск:** `docker compose up -d`.
9. **Проверка** (раздел 5).

## 6. Инструкция по использованию

| Действие | Команда |
|---|---|
| Собрать и запустить (после изменений в коде) | `docker compose up -d --build` |
| Посмотреть логи | `docker compose logs -f` |
| Перезапустить | `docker compose restart` |
| Остановить (данные сохраняются) | `docker compose down` |
| Состояние контейнера | `docker compose ps` |
| Проверить бэкапы базы | `docker compose exec app node scripts/backup-verify.js` |

Адреса после запуска: сайт — http://localhost:3000, админка — http://localhost:3000/admin.

## 7. Возникшие сложности и их решение

| Проблема | Решение |
|---|---|
| Сервер по умолчанию слушает только `127.0.0.1` и внутри контейнера был бы недоступен | Переменная `HOST=0.0.0.0` в образе; снаружи порт всё равно открыт только на `127.0.0.1` хоста |
| Порт 3000 был занят работающим сайтом | Тестирование образа на порту 3001, затем плановое переключение |
| Старый сервер автоматически перезапускался супервизором и планировщиком | Удалена задача `ZhanaraSite`, остановлены супервизор и сервер |
| SQLite ненадёжно работает на папках Windows, подключённых в контейнер | Использованы именованные тома Docker; данные перенесены через `docker compose cp` |
| Скопированные файлы принадлежали root, а приложение работает от `node` | Смена владельца командой `chown` во временном контейнере |
| Риск попадания секретов в образ | `.env` исключён через `.dockerignore`, подключается через `env_file` при запуске |

## 8. Выводы

Приложение полностью контейнеризовано. Сборка фронтенда, установка зависимостей и запуск сервера выполняются внутри Docker, на компьютере нужен только сам Docker. Итоговый образ содержит только то, что нужно для работы: без исходников фронтенда, инструментов сборки, тестов и секретов. Данные хранятся в отдельных томах и не теряются при обновлении. Рабочий сайт переведён на Docker без потери данных: перед переносом сделана резервная копия, после переноса работоспособность проверена.

Возможные улучшения:

- настроить reverse proxy (nginx или Caddy) с HTTPS для публичного доступа;
- добавить Telegram-токены, чтобы включить уведомления о заявках;
- настроить автоматическую сборку образа (CI) и публикацию в реестр образов.
